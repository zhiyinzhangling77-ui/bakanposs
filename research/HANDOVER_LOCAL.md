## 1. **ローカルに移ることで何が変わるか**

### 1-1. **二台構成が消える**
**これまでは「コンテナ（合成・道具づくり）」と「あなたの PC（`/mnt/hdd` の実データ）」に割れていた。**
**私は実データを一度も見られず、あなたが出力を貼る往復で進めていた。**

**ローカルでは両方が同じ場所にある。** **その結果**：

| これまで | ローカルでは |
|---|---|
| 実データの実行は `HUMAN_GATES.md` に積む | **その場で走らせる** |
| 出力を貼ってもらう往復 | **不要** |
| 「1 回のローカル実行で最大数の GATE を片付ける」設計 | **その最適化は不要になる** |
| コンテナで Python が動かない周があった（旗103） | **動く。旗104 で本人が訂正済み** |

**＝`HUMAN_GATES.md` の「ローカル実行」種別のゲートは、ほぼ全部その場で消化できる。**
**残る人間待ちは「判断」と「外部への連絡」だけになる。**

### 1-2. **だが、緩めてはいけないもの**
**実データがすぐ触れることは、作法を緩める理由にならない。**

> **合成での検証を先に通す順序は、そのまま守る。**
> **旗89・91・93×2・96・97・100・102・104・106・107・109 の 12 回、
> 合成が実データ前に設計の欠陥を捕まえている。**
> **実データが手元にあると、この工程を飛ばしたくなる。飛ばさない。**

**事前登録も同じ。** **「すぐ走らせられる」ことは「先に答えを見てよい」ことではない。**

### 1-3. **出力の記録**
**`research/runlog.py` が主要 12 本の道具に入っている**（旗110・欠陥 #42）。
**走らせると自動で `research/logs/<名前>_<日時>.txt` に画面と同じものが残る**（stderr の警告も含む）。
**`tee` を打つ必要は無い。**

**注意**：**ログは repo に入る。** **146 サイトの掃引は数百 KB。**
**溜まりすぎたら整理するか `.gitignore` に入れるかを決める**（**まだ決めていない**）。

## 6. **作法**（旗100–113 で加わったもの・**全 13 項目**）

1. **否定側の合成は、肯定側と同じ関門を通る強さで作る**（旗100）
2. **前提にする物理の「向き」を、合成で確かめてから予測を書く**（旗102）
3. **率どうしを比べる下限は 10 本**（旗102 で 3 本では何も判別できなかった）
4. **★をどの窓で測るかを、事前登録に必ず書く**（旗100）
5. **合成の対照は「名乗る性質を実際に持っている」ことを数値で確かめる**（旗104/106）
6. **合成の枝が通っても、実データの枝は別に確かめる**（旗106・欠陥 #37）
   **少なくとも関数の署名と戻り値の形を `ast`＋`inspect` で照合する**
7. **CI が 0 を外れることと、意味のある大きさであることは別**（旗109・`DELTA_FLOOR`）
8. **判定規則はクラスタで書く。サイトで書かない**（旗106 の反省）
9. **「全部」を数えるときは、コード自身が持つ列挙を使う**（旗108・欠陥 #39）
10. **落ちた理由を一つの籠に入れない。原因ごとに数える**（旗108・欠陥 #40）
11. **別々の登録簿から来た量を並べるときは、単位を確かめる**（旗110・欠陥 #41）
12. **出力は最初からファイルに残す**（旗110・欠陥 #42）
13. **分離したことは、正しく分離したことを意味しない。
    較正集合の外に答えの分かる例があるなら、必ず当てる**（旗112）

**これ以前の作法は `LOOP_PROTOCOL.md` の「絶対にやってはいけないこと」10 項目にある。**

## 7. **1 周の型**（**変えない**）

```
①下調べ（feasibility のみ・相関も Δ も計算しない）
   → ②事前登録（前提の事実確認 → 手順 → 判定規則 → 予測 → 限界）
   → ③合成で検証（期待する枝に実際に到達するかを数値で確かめる）
   → ④欠陥が出たら追補を書いて commit（実データ前）
   → ⑤実データを走らせる
   → ⑥FLAGS_LOG に結果・留保・道具の欠陥を書く
   → ⑦commit・push
```

**②と③の間に実データを見ない。** **⑤の後に判定規則を変えない。**
